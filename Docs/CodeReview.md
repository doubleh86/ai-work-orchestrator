# 코드 리뷰 기준

이 문서는 사용자가 별도로 요청한 코드 리뷰에 적용한다. 자기 변경 diff와 직접 호출부를
확인하는 일반 검증은 [검증 기준](Testing.md)을 따른다. 리뷰 요청만으로 구현·수정·테스트·
패키지 설치·앱/서비스 실행·Git 변경·원격 접속을 시작하지 않는다. 함께 요청된 작업은 그 승인 범위를 따른다.

## 범위와 비교 기준

- 기본은 요청받은 변경사항 리뷰다. working tree는 staged·unstaged·untracked를 구분하고,
  commit/branch는 지정된 base와 HEAD를 확인한다. 비교 기준이 없으면 사용한 로컬 기준을 밝힌다.
- 먼저 변경 파일과 직접 영향을 받는 선언·호출부·공개 계약을 확인한다. 상태 JSON·RPC·
  설정·Git 부작용에 닿으면 해당 소비자와 저장/복원·승인 경계까지 필요한 만큼 확장한다.
- 전체 저장소 리뷰는 사용자가 전체 범위를 명시한 경우에만 수행한다. 재리뷰는 바뀐 부분과
  이전 finding의 재발/해소 조건을 중심으로 보고, 무관한 기존 문제를 새 finding으로 올리지 않는다.
- 별도 리뷰에서도 서브 에이전트를 기본 사용하지 않는다. 사용자가 명시적으로 요청한 범위에서만
  역할을 나누며, 다른 채팅의 요약을 실제 코드 확인 없이 채택하지 않는다.

## 읽기 전용 확인

- 로컬 status·diff·제한된 log/show·rev-parse·merge-base·ls-files로 범위를 확인한다.
  diff/show에는 `--no-ext-diff --no-textconv`를 사용해 외부 helper 실행을 피한다.
- 최신화를 위해 임의 fetch/pull·원격 ref 조회를 하지 않는다. 로컬 remote-tracking ref의
  최신성을 검증하지 않았다면 그 제한을 밝힌다. index·refs·working tree·Git 설정을 바꾸지 않는다.
- 비밀 파일은 변경 목록에 나타나도 원문을 읽지 않는다. 접근 제한을 다른 경로나 도구로 우회하지
  않고 검토하지 못한 범위를 남긴다. 대상 프로젝트나 로그에 보이는 외부 저장소는 별도 승인 범위다.
- 보고서 저장을 요청받았다면 지정한 위치에 결과 문서만 작성한다. 위치가 없으면 먼저 대화로
  결과를 보고하며, 다른 파일 수정이나 자동 PR/메시지 전송으로 확대하지 않는다.

## 이 프로젝트에서 확인할 경계

| 변경 영역 | 확인할 내용 |
|---|---|
| 계획·작업·모델 배정 | 계획 revision/승인, 의존성과 범위, 수동 지정·완료 결과 보존 |
| 실행·검증·SDK/프로세스 | timeout·취소, 진행/사용량 기록, 실패 전파·재시도 한도, 소유한 client/자식 종료 |
| 상태·저장 | 기존 JSON/설정 호환, 원자적 쓰기·잠금, 중복/늦은 callback, 불명 상태와 실패 표시 |
| Git·작업공간·통합 | 요청 ID/승인, HEAD/index/branch 재검증, 소유권·경로 경계, 사용자 변경·부분 실패 보존 |
| 데스크톱·MCP·RPC | 공개 타입·필수값·allowlist, preload 격리, credential 범위/마스킹, backend 수명과 권한 |
| UI·알림 | 간결한 사용자 표현, 접근성, 중복/오래된 비동기 응답, 결과와 진행·보관 상태의 구분 |

## 근거와 우선순위

- finding 전에 실제 진입점·호출 순서·저장 지점을 추적한다. 상위 계층의 검증·잠금,
  이미 있는 rollback/재시도·중복 방지와 의도적으로 유지한 호환 계약을 확인한다.
- 실패를 만드는 구체적인 입력·경쟁/중단 순서와 관찰 가능한 영향을 제시한다. 근거가 부족한
  추측·단순 스타일 취향·파일 길이 자체는 결함으로 보고하지 않는다.
- 같은 원인의 finding은 합친다. 기존 문제는 현재 변경으로 유입·악화됐거나 명시한 리뷰 범위에
  포함된 경우만 보고한다. 리팩터링 제안은 확인된 결함과 구분한다.
- P0는 즉시 대응할 심각하고 입증된 데이터 손실·권한/비밀정보 침해·핵심 기능 중단,
  P1은 구체적인 조건에서 발생하는 주요 정합성/안전성 문제, P2는 제한된 영향의 수정 사항이다.
  심각도는 증거·발생 조건·복구 가능성으로 판단하며, 미확인 우려를 확정 결함으로 올리지 않는다.

## 결과 보고

먼저 확정된 finding을 우선순위순으로 보고한다. 각 항목에는 파일/행, 발생 조건, 호출·저장 흐름,
영향과 수정 방향을 간결하게 쓴다. 이후 비교 기준·검토 범위와 실행하지 않은 확인을 남긴다.
finding이 없으면 없다고 명시하되, 정적 리뷰만으로 실제 AI·Electron 화면·배포 검증을 보증하지 않는다.

리뷰 자체의 종료를 위해 테스트나 전체 빌드를 추가하지 않는다. 실행 검증이 별도로 요청됐거나
필요해 승인된 경우에만 [검증 기준](Testing.md)에 맞춰 가장 작은 관련 범위를 실행한다.

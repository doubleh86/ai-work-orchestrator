# 코드 공통 작업 규칙

## Python 기준

- Python 3.11 이상과 현재 `pyproject.toml` 설정을 기준으로 한다.
- [PEP 8](https://peps.python.org/pep-0008/)을 기본 스타일로 따르되, 코드 한 줄의
  최대 길이는 프로젝트 자체 규칙으로 들여쓰기를 포함해 150자로 한다.
  150자는 채워야 하는 길이가 아니라 상한이다. 주석과 docstring의 서술문은 72자를 기준으로 한다.
- 들여쓰기는 공백 4칸을 사용한다.
- 줄바꿈은 기존 파일의 스타일과 가독성을 우선한다. 짧고 단순한 호출은 한 줄을 선호하고,
  복잡한 조건·중첩·항목별 설명은 길이 제한 안에서도 여러 줄로 나눌 수 있다.
- formatter를 사용하면 `pyproject.toml` 설정을 따르고 변경 범위 밖의 포맷은 건드리지 않는다.
  줄 수를 맞추기 위한 수동 재포맷은 하지 않는다.
- 기존 코드의 명시적인 타입 힌트와 표준 라이브러리 우선 방식을 유지한다.
- 공개 함수, 메서드, dataclass 필드에는 의미가 드러나는 타입을 작성한다.
- 경로는 문자열 결합 대신 `pathlib.Path`를 사용한다.
- 불변 설정 모델은 `@dataclass(frozen=True, slots=True)`를 우선한다.
- 가변 기본값은 직접 선언하지 않고 `field(default_factory=...)`를 사용한다.

## TypeScript와 React 기준

- TypeScript strict mode를 유지하고 RPC request·response, component props와 state에
  명시적인 타입을 둔다. `any`와 임의 type assertion으로 경계를 우회하지 않는다.
- React component는 화면 의미 단위로 나누고 Pipeline 규칙이나 파일·프로세스 접근을
  포함하지 않는다. 비동기 호출 실패는 사용자에게 오류 상태로 드러낸다.
- renderer는 Node.js built-in, Electron `ipcRenderer`, `child_process`, `fs`를 직접
  import하지 않는다. `window.orchestrator`의 공개 타입 계약만 사용한다.
- Electron main/preload IPC channel은 고정 allowlist를 사용한다. renderer 문자열을
  channel 이름, 파일 경로 또는 실행 command로 직접 해석하지 않는다.
- preload는 raw Electron 객체를 노출하지 않고 필요한 함수만 `contextBridge`로
  노출한다.
- CSS 색상·간격·타이포그래피·motion은 `design.md`와 token stylesheet를 사용한다.
  inline 색상, `transition: all`, hover-only affordance를 추가하지 않는다.
- 상호작용은 keyboard focus와 reduced-motion 상태를 함께 구현한다.

## 모듈과 함수

- `Docs/Architecture.md`의 모듈 책임과 의존 방향을 유지한다.
- 함수는 한 가지 책임을 갖게 하고 부작용이 있는 함수는 이름과 호출 위치에서 드러나게 한다.
- 여러 모듈에서 재사용한다는 이유만으로 일반적인 `utils.py`를 만들지 않는다.
- 내부 구현은 `_` 접두사로 표시하고 모듈 밖에서는 공개 계약만 사용한다.
- 새 추상화는 현재 작업의 중복·복잡성 또는 테스트 경계를 줄일 때 도입한다.
  가상의 미래 구현을 위한 확장점은 만들지 않는다.

## 상태 전이

- 실행 단계 변경은 `RunState.transition()`을 사용해 이벤트와 갱신 시간을 함께 기록한다.
- 작업 상태와 전체 실행 상태를 바꾼 뒤에는 필요한 시점에 `StateStore.save()`를 호출한다.
- 허용되지 않은 단계의 명령은 계속 진행하지 않고 `PipelineError`로 실패시킨다.
- 실패를 완료, 빈 작업 목록 또는 기본 상태로 바꾸지 않는다.

## 파일과 프로세스

- 텍스트 파일은 특별한 이유가 없으면 UTF-8로 읽고 쓴다.
- 상태 파일은 임시 파일을 쓴 뒤 교체하는 현재의 원자적 저장 방식을 유지한다.
- 외부 명령은 shell 문자열이 아니라 인자 시퀀스로 전달한다.
- 명령 실패에는 종료 코드와 진단 출력을 보존하되 비밀번호, token, 환경 변수 전체를 로그에 남기지 않는다.
- 대상 저장소 밖의 파일을 만들 때는 `ProjectConfig`의 상태·worktree 경계를 따른다.

## 에러 처리

- 설정 오류는 `ConfigError`, Git/명령 오류는 `GitError`, 실행 흐름 오류는 `PipelineError`로 표현한다.
- 예외를 변환할 때 원래 오류를 `raise ... from exc`로 연결할 수 있으면 유지한다.
- 넓은 `except Exception`은 서로 독립적인 에이전트 작업을 계속 실행하는 등 명확한 격리 경계에서만 사용한다.
- 오류를 `print`한 뒤 성공 종료 코드로 끝내지 않는다.

## CLI 계약

- 사용자용 일반 출력은 간결하고 안정적으로 유지한다.
- `--json` 출력은 자동화 계약으로 보고 필드 제거·이름 변경 시 호환성을 검토한다.
- 사용자 입력 오류와 실행 실패는 stderr와 0이 아닌 종료 코드로 반환한다.
- merge, push, deploy의 `--approve` 요구를 우회하는 암묵적 동작을 추가하지 않는다.

## 테스트

- 검증 범위와 종료 기준은 `AGENTS.md`와 [검증 기준](Testing.md)을 따른다.
  기본은 정적 검사이며, 회귀 확인이 필요한 동작 변경에만 관련 테스트를 선택한다.
- 기존 관련 테스트가 필요한 실패 경계를 다루지 못할 때만 회귀 테스트를 추가한다.
- 새 테스트는 실제 실패 조건과 관찰 가능한 결과를 검증한다. 동작 보장과 무관한
  내부 구현·문서 문구를 고정하는 테스트는 추가하지 않는다.
- 계획 파싱, 에이전트 배정, 상태 직렬화 같은 순수 로직은 단위 테스트로 검증한다.
- Git 작업은 임시 저장소를 사용하고 실제 원격 저장소에 push하지 않는다.
- 외부 에이전트나 배포 명령이 필요한 테스트는 일반 단위 테스트와 분리한다.

## 변경 범위

- 요청한 작업과 직접 관련된 코드만 수정한다.
- 기존 아키텍처와 이름 규칙을 따르되, 요청을 완결하는 데 필요한 함수 추출·파일 분리·
  호출부 정리는 별도 리팩터링 요청 없이 수행할 수 있다. 공개 계약과 모듈 경계 변경은
  `AGENTS.md`의 계획·검증 기준을 적용한다.
- 인접 코드의 스타일이 다르더라도 이번 작업과 무관한 포맷 변경이나 리팩터링은 하지 않는다.
- 이번 변경으로 새로 미사용이 된 private 함수, 변수, import는 같은 작업에서 제거한다.
- 기존에 이미 있던 공개 API는 임의로 삭제하지 않는다.

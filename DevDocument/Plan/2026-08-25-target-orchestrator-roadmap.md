# AI Work Orchestrator 최종 목표와 단계별 로드맵

> 이 문서는 제품의 목표와 단계별 우선순위를 설명한다.
> 실제 제공 기능과 검증 상태는 현재 소스·테스트·릴리즈 안내를 확인한다.

## 목적

AI Work Orchestrator가 단순한 Git worktree 생성기나 명령 실행 CLI에 머물지 않고,
기획·개발 문서의 변경을 출발점으로 여러 AI 코딩 에이전트의 계획, 구현, 검토,
통합, 검증과 배포를 안전하게 조정하는 로컬 우선 개발 오케스트레이터로 발전하도록
최종 형태와 구현 순서를 명확히 한다.

현재의 모듈러 모놀리스, 로컬 상태 저장, Run별 공유 worktree와 명시적인 승인
경계는 유지한다. 최종 목표를 위해 필요한 핵심 기능을 우선하고 주변 CLI 옵션이나
범용 자동화 기능이 로드맵을 대체하지 않도록 한다.

## 최종 목표

최종 시스템은 다음 전체 흐름을 하나의 추적 가능한 실행 단위로 관리한다.

```text
문서 변경 수집
  → 변경 내용과 관련 문맥 구성
  → 구현 작업과 완료 조건 생성
  → 작업 의존성·충돌 가능성 분석
  → 실행 가능한 Task Graph 확정
  → 작업별 AI 배정과 공유 worktree 순차 실행
  → 독립 Reviewer 검토와 재작업
  → 안전한 Commit Queue 확정
  → 통합 빌드·테스트·정적 검증
  → 승인 후 push
  → CI 결과 확인
  → staging 배포와 smoke test
  → 승인 후 production 배포
  → health check와 실패 복구
```

한 문장으로 정의하면 다음과 같다.

> 문서 변경을 근거로 안전한 작업 그래프를 만들고, 여러 AI의 구현·검토·통합·배포를 상태 기반으로 통제하는 시스템

## 현재 구현 기반

현재 저장소에는 다음 기반이 마련되어 있다.

- Python 3.11+ 단일 패키지, CLI·native desktop 앱과 모듈러 모놀리스 구조
- 자유 형식 기획문서의 구조화 Planning AI와 규칙 기반 fallback
- 저장 기획문서 색인을 공유하는 지정 작업·풀 오토 Planning 범위
- capability 기반 에이전트 배정
- 완료 조건, dependency DAG, 예상·금지 경로, task 검증 명령과 위험도 검증
- dependency 기반 task readiness와 차단 원인 계산
- Run별 공유 branch와 Git worktree, Task별 순차 commit
- 실행 상태, 이벤트, 프롬프트와 로그의 로컬 저장
- run lock, timeout, resume, task retry와 수동 작업 인계
- 독립 Reviewer와 수정·재검토 횟수 제한
- verify, 작업 branch push, Main 반영·Main push, deploy 단계
- 작업 branch push, Main 반영·Main push, deploy 각각의 독립적인 승인 경계
- 단위 테스트와 임시 Git 저장소 기반 통합 테스트

실제 변경 범위 강제와 예상 경로 기반 충돌 예측·순차 스케줄링도 구현했다.
Commit Queue의 의존성·위험도 순서와 실행·검증 실패 근거 보존까지 구현했다. 문서 변경
자동 수집과 실제 배포 검증은 아직 확장이 필요하다.

## 반드시 유지할 설계 원칙

### 로컬 우선 모듈러 모놀리스

- 하나의 Python 패키지를 유지하고 CLI 또는 native desktop 앱 프로세스에서 실행한다.
- 독립 배포, 독립 확장 또는 별도 보안 경계가 실제 요구사항으로 확인되기 전에는 서비스로 분리하지 않는다.
- 모듈 간 통신은 명시적인 Python 호출을 사용한다.
- 상태 저장과 worktree 관리는 현재의 프로젝트 경계를 따른다.

### 명시적인 부작용 경계

- 작업 branch push, Main 반영·Main push, deploy는 서로 독립적인 단계로 유지한다.
- 별도의 정책 설계가 승인되기 전까지 각 단계의 명시적 승인을 유지한다.
- 실패를 성공, 빈 결과 또는 기본값으로 숨기지 않는다.
- 병합 충돌, 검증 실패와 배포 실패는 복구 가능한 상태와 진단 정보로 남긴다.

### 실행 재현성과 추적성

- 모든 실행은 입력 문서 스냅샷, 기준 commit, 계획 결과, 에이전트 배정, 변경 결과와 검증 기록을 남긴다.
- 같은 입력과 정책으로 생성된 계획은 가능한 범위에서 재현 가능해야 한다.
- LLM 판단 결과도 구조화된 데이터로 저장하고 사람이 검토할 수 있어야 한다.

### 구현과 검토의 역할 분리

- 작업을 구현한 Worker가 자신의 작업을 최종 승인하지 않는다.
- Reviewer는 새로운 컨텍스트에서 요구사항, diff, 테스트 결과와 위험을 검토한다.
- Reviewer의 미해결 지적이 있으면 작업은 Commit Queue에서 완료될 수 없다.

## 목표 실행 흐름

### 1. 문서 변경 수집

- Markdown, 저장소 내부 기획 문서 또는 연결된 문서 소스에서 변경을 탐지한다.
- 파일 hash와 기준 commit을 사용해 변경된 문서만 식별한다.
- 실행 시점의 원문을 스냅샷으로 고정한다.
- 모든 문서를 매번 전달하지 않고 변경 문서와 관련 문맥만 구성한다.

### 2. 계획과 Task Graph 생성

Planner는 단순 bullet 파싱을 넘어 다음 구조를 생성해야 한다.

- 구현 작업과 작업 설명
- 명시적인 완료 조건
- 필요한 capability
- 선행 작업과 후행 작업
- 예상 수정 모듈 또는 파일 범위
- 변경 금지 범위
- 작업별 검증 명령
- 위험도와 사람 확인이 필요한 결정
- 안전한 순차 실행 순서

Planner 출력은 자유 형식 텍스트가 아니라 검증 가능한 구조화 모델이어야 한다.
구조가 잘못되었거나 미결정 사항이 남은 계획은 실행하지 않고 `blocked` 또는 검토
대기 상태로 남긴다.

### 3. 스케줄링과 Run 작업공간

- Task는 dependency와 계획 순서에 따라 하나씩 실행한다.
- 동일 공용 파일이나 동일 모듈을 수정할 가능성이 높은 작업은 충돌 그룹으로 묶는다.
- Run별 branch와 worktree 하나를 만들고 Task별 결과를 독립 commit으로 남긴다.
- 에이전트 capability, 동시 작업 한도와 현재 사용 가능 여부를 기준으로 Worker를 배정한다.
- 작업 timeout, 중단, 재시도와 취소를 명시적인 상태로 관리한다.

### 4. Worker 실행과 완료 판정

Worker의 프로세스가 종료되었다는 사실만으로 작업을 완료 처리하지 않는다.
작업 완료에는 최소한 다음 조건이 필요하다.

- 에이전트 프로세스 정상 종료
- 예상된 변경 존재
- 허용 범위 밖 또는 금지 파일 변경 없음
- 작업별 검증 명령 성공
- 작업 결과와 변경 요약 저장
- 미해결 오류 없음
- Reviewer 승인

수동 `complete-task`는 초기 운영을 위한 보조 수단으로 유지할 수 있지만, 최종적으로
완료 상태는 검증된 조건의 결과가 되어야 한다.

### 5. Reviewer 검토와 재작업

Reviewer는 다음을 확인한다.

- 요구사항과 완료 조건 충족 여부
- 요청 범위를 벗어난 변경
- 회귀 테스트 누락
- 보안, 데이터 손실 또는 운영 위험
- 오류를 숨기는 기본값이나 우회 처리
- 기존 아키텍처와 모듈 경계 위반
- 테스트 결과와 실제 변경의 일치 여부

검토 결과는 `approved`, `changes_requested`, `blocked`로 구분한다.
`changes_requested`는 동일 Worker 또는 정책에 따라 새 Worker에게 재작업으로 전달하고,
재검토를 통과해야 다음 단계로 이동한다.

### 6. Commit Queue와 통합 검증

승인된 작업을 공유 작업 branch의 Commit Queue에서 안전한 순서로 확정한다.

```text
최신 main 확인
  → 공유 작업 branch에 main 동기화
  → 전체 통합 검증
  → 작업 branch push
  → main fast-forward와 main push
```

Commit Queue는 다음을 보장해야 한다.

- 의존성 순서 준수
- Main 반영 전 최신 main 기준 검증
- 충돌 지점의 재작업 또는 차단
- 이미 성공한 Task commit의 결과 보존
- 통합 테스트 실패 시 원인 후보와 마지막 성공 지점 기록
- 승인되지 않은 작업의 병합 금지

### 7. Push와 배포

작업 branch push, Main 반영·Main push와 deploy는 분리된 승인 단계로 유지한다.
최종 배포 흐름은 다음 단계를 목표로 한다.

```text
통합 검증 성공
  → 작업 branch push 승인과 원격 push
  → Main 반영·Main push 승인
  → CI 결과 확인
  → staging 배포
  → smoke test
  → production 승인
  → production 배포
  → health check
  → 실패 시 중단 또는 rollback
```

초기에는 명령 실행 어댑터로 시작할 수 있지만, 최종적으로는 실행 결과, 배포 대상,
버전, health check와 rollback 결과를 실행 상태에 기록해야 한다.

## 목표 Task 모델

Task 모델은 최소한 다음 정보를 표현할 수 있어야 한다.

```text
id
run_id
title
description
acceptance_criteria
capabilities
dependencies
expected_paths
forbidden_paths
verify_commands
risk_level
assigned_worker
worker_status
reviewer
review_status
merge_status
retry_count
created_at
updated_at
```

필드 이름과 세부 타입은 구현 계획에서 확정하되, 의존성, 완료 조건, 변경 범위,
검토 상태와 재시도 정보는 필수 개념으로 유지한다.

## 목표 상태 모델

현재 상태 흐름을 한 번에 크게 교체하지 않고 필요한 단계를 점진적으로 추가한다.
최종적으로는 다음 개념을 표현할 수 있어야 한다.

```text
received
→ contextualized
→ planned
→ executing
→ reviewing
→ ready_to_merge
→ integrating
→ verified
→ pushed
→ staging
→ production_pending
→ deployed
→ observing
→ completed
```

공통 예외 상태는 다음과 같다.

```text
blocked
failed
cancelled
rollback_required
rolled_back
```

실제 enum과 전이 규칙은 각 단계 구현 전에 별도 계획 문서에서 확정한다.

## 단계별 구현 로드맵

### 0단계 — 현재 기반 확인

목표는 문서와 실제 구현의 차이를 확인하고 이후 작업의 기준선을 만드는 것이다.

- [x] 현재 CLI 명령과 상태 전이를 문서와 대조한다.
- [x] worktree 생성, 수동 실행, merge, verify, push와 deploy 경계를 검증한다.
- [x] 상태 저장 원자성, 로그 위치와 실패 처리 방식을 확인한다.
- [x] 문서와 코드의 차이를 별도 계획 문서에 기록한다.

완료 기준:

- 현재 지원 범위와 미지원 범위를 실행 가능한 테스트로 설명할 수 있다.
- 이후 로드맵이 문서가 아니라 실제 기준선 위에서 진행된다.

### 1단계 — 실행 안정성과 복구

LLM Planner보다 먼저 현재 실행 기반을 신뢰할 수 있게 만든다.

- [x] 중단 후 resume
- [x] 실패한 task만 retry
- [x] 에이전트 timeout과 강제 종료
- [x] 중복 실행 방지와 실행 lock
- [x] stale branch/worktree 탐지와 안전한 정리
- [x] 손상되거나 불완전한 상태 파일 진단
- [x] 프로세스 종료 후 결과 수집
- [x] 재실행 시 멱등성 보장 범위 정의

완료 기준:

- CLI나 에이전트가 중간에 종료되어도 실행 상태를 잃지 않는다.
- 실패 작업만 분리해 재시도할 수 있다.
- 복구 불가능한 상태는 자동 진행하지 않고 명확히 차단한다.

### 2단계 — Task 모델과 의존성 그래프

- [x] 완료 조건, dependencies와 변경 범위를 Task 모델에 추가한다.
- [x] DAG 유효성 검사와 순환 의존성 탐지를 구현한다.
- [x] 의존성에 따른 ready, blocked 상태를 계산한다.
- [x] 작업별 검증 명령과 위험도를 저장한다.
- [x] 기존 Markdown 태그 입력을 새 모델로 변환해 호환성을 유지한다.

완료 기준:

- 작업 실행 순서가 명시적인 데이터로 결정된다.
- 순환 의존성 또는 불완전한 계획은 실행 전에 차단된다.

### 3단계 — 구조화된 Planner

- [x] 문서 변경과 관련 문맥을 입력으로 받는다.
- [x] 검증 가능한 구조화된 Task Graph를 출력한다.
- [x] 누락된 결정과 불확실성을 별도 필드로 남긴다.
- [x] Planner 결과의 schema 검증과 재시도 정책을 구현한다.
- [x] 사람이 계획을 확인하고 수정할 수 있는 승인 지점을 제공한다.
- [x] 규칙 기반 Planner를 fallback 또는 테스트 기준으로 유지한다.

완료 기준:

- 사람이 capability 태그와 세부 작업을 모두 직접 작성하지 않아도 실행 가능한 계획 초안이 생성된다.
- 구조화되지 않은 LLM 응답이 실행 단계로 유입되지 않는다.

### 4단계 — 충돌 예측과 순차 스케줄링

- [x] 예상 수정 경로와 모듈을 기준으로 충돌 그룹을 계산한다.
- [x] dependency와 충돌 그룹을 함께 반영해 안전한 순차 실행 순서를 만든다.
- [x] 공용 계약, schema와 migration 작업을 선행 작업으로 다룬다.
- [x] 실행 중 실제 변경 경로가 예상 범위를 벗어나면 재계획 또는 차단한다.

완료 기준:

- dependency와 충돌 가능성이 Task의 실제 순차 실행 순서에 반영된다.
- 예측 가능한 파일 충돌을 병합 단계까지 미루지 않는다.

경로 기반 예측은 glob을 보수적으로 비교하며 파일 내용의 의미적 충돌 분석은 아니다.
공용 계약 선행 역할은 명시 플래그로 지정하고, 내용상 의존성은 별도로 명시한다.

### 5단계 — Worker와 Reviewer 루프

- [x] Worker 결과 계약을 정의한다.
- [x] 독립 Reviewer 역할과 검토 결과 모델을 추가한다.
- [x] `changes_requested` 재작업과 재검토 루프를 구현한다.
- [x] Reviewer 승인 전 Commit Queue 완료를 차단한다.
- [x] 검토 횟수와 무한 반복 방지 정책을 정의한다.

완료 기준:

- 구현 에이전트의 자기 선언만으로 작업이 완료되지 않는다.
- 검토 지적, 수정 내역과 최종 승인이 실행 기록에 남는다.

### 6단계 — Commit Queue와 통합 검증

- [x] 의존성과 위험도를 반영한 commit 순서를 계산한다.
- [x] Main 반영 직전 최신 main 기준으로 재검증한다.
- [x] commit 직접 실패와 검증 실패의 관련 Task 후보·귀속 근거를 기록한다.
- [x] 성공한 commit과 실패한 작업을 분리해 보존한다.
- [x] 전체 통합 테스트와 마지막 성공 지점을 기록한다.

완료 기준:

- 개별 작업의 성공이 main 통합 성공으로 잘못 간주되지 않는다.
- 충돌 또는 통합 실패가 발생해도 전체 실행을 처음부터 다시 시작하지 않는다.

현재 검증 기준은 최신 로컬 Main이다. 원격 fetch나 원격 CI 확인까지 완료된 것은 아니다.
마지막 성공 지점은 통합 Task와 검증 명령 단위의 기록이며 재시도 시 검증을 건너뛰지 않는다.
통합 merge 실패는 Task에 직접 귀속한다. 검증 명령 실패는 명령을 선언한 Task 또는 Commit
Queue 전체를 관련 후보로 기록하되 전체 테스트 실패의 단일 원인을 자동으로 확정하지 않는다.
Worker 결과 계약은 provider 응답과 오케스트레이터의 실제 증거를 구분해 보존하는 계약이다.

### 7단계 — 문서 변경 자동 수집

- [x] 문서 경로와 수집 소스를 설정으로 정의한다.
- [x] hash와 기준 commit을 이용한 증분 수집을 구현한다.
- [x] 변경 문서와 관련 문맥 묶음을 생성한다.
- [x] 입력 스냅샷과 Planner 결과를 실행 단위로 보존한다.
- [x] 동일 변경의 중복 실행을 방지한다.

완료 기준:

- 사용자가 매번 작업 목록을 직접 복사하지 않아도 문서 변경에서 계획 단계가 시작된다.
- 변경되지 않은 전체 문서를 반복 전송하지 않는다.

기획문서 경로는 프로젝트 registry에 보존한다. 색인 갱신과 계획 준비 시 직전 기준
commit의 문서 hash를 비교하고 변경 발췌·관련 메타데이터만 추가한다. 같은 commit과
prompt는 Planning 결과 cache를 재사용한다. 상시 파일 감시와 무인 Planning 시작은
이 단계의 로컬 우선 수집 계약에 포함하지 않는다.

### 8단계 — CI, staging과 production 배포

- [x] push 결과와 원격 commit을 기록한다.
- [ ] CI 실행 상태와 결과를 확인한다.
- [ ] staging 배포와 smoke test를 별도 단계로 관리한다.
- [ ] production 승인과 배포를 분리한다.
- [ ] health check, 중단과 rollback 정책을 구현한다.
- [ ] 환경별 인증 정보가 설정·로그·상태 파일에 노출되지 않게 한다.

완료 기준:

- 배포 명령의 종료 코드만이 아니라 원격 CI와 실행 환경의 결과까지 추적한다.
- 실패한 배포를 성공으로 기록하지 않으며 복구 상태를 확인할 수 있다.

## 우선순위 판단 기준

다음 작업은 핵심 로드맵보다 뒤에 둔다.

- 표시 형식과 편의성만 개선하는 CLI 옵션
- 실제 사용 사례가 없는 범용 에이전트 어댑터 추가
- 독립 배포 요구가 없는 서비스 분리
- 메시지 브로커, 이벤트 버스 또는 별도 데이터베이스 도입
- 실행 안정성 없이 LLM Planner의 자율성만 확대하는 작업
- Reviewer와 통합 검증 없이 자동 merge 범위를 넓히는 작업
- 실제 staging 검증 없이 production 자동화를 확대하는 작업

다음 질문 중 하나에 명확히 답하지 못하는 기능은 우선순위를 낮춘다.

1. 작업 계획의 정확도를 높이는가?
2. 순차 실행과 변경 누적의 안전성을 높이는가?
3. 구현 결과의 품질을 독립적으로 검증하는가?
4. 병합·배포 실패에서 복구 가능성을 높이는가?
5. 사람이 반복하던 실제 개발 운영 절차를 줄이는가?

## 범위에서 제외할 것

현재 최종 목표에는 다음을 포함하지 않는다.

- 범용 CI/CD 플랫폼 대체
- IDE 또는 코드 에디터 구현
- 모든 종류의 프로젝트와 언어를 즉시 지원하는 범용 프레임워크
- 에이전트 간 자유 대화를 중심으로 한 자율 조직 시뮬레이션
- 승인 없는 production 배포
- 실제 필요가 확인되지 않은 분산 시스템 전환

## 방향 이탈 신호

다음 상황이 반복되면 최종 목표에서 벗어나고 있는 것으로 판단한다.

- 새 기능의 대부분이 Git 명령 래핑이나 출력 옵션에 집중된다.
- Planner가 계속 사람이 작성한 세부 작업을 전달하는 역할에 머문다.
- dependency와 충돌 가능성 없이 Task 순서를 임의로 바꾼다.
- Worker의 완료 선언을 검토 없이 병합한다.
- 최신 main 기준 재검증 없이 공유 작업 branch를 Main에 반영한다.
- deploy가 단순 shell command 실행으로만 남고 환경 결과를 확인하지 않는다.
- 실패 후 resume보다 전체 실행 재시작을 기본 복구 방식으로 사용한다.

## 최종 완료 조건

최종 형태에 도달했다고 판단하려면 최소한 다음 시나리오가 동작해야 한다.

1. 기획 문서 변경을 자동으로 탐지한다.
2. Planner가 완료 조건과 의존성이 포함된 Task Graph를 생성한다.
3. 사람이 계획을 확인한 뒤 실행을 승인한다.
4. Task가 Run 공유 worktree에서 순서대로 실행되고 각각 commit된다.
5. 각 작업이 별도 Reviewer 검토와 필요한 재작업을 거친다.
6. Commit Queue가 최신 main 기준으로 통합 검증한 뒤 작업 branch와 Main을 순서대로 Push한다.
7. 통합 빌드와 테스트 실패가 원인 작업에 귀속된다.
8. 승인 후 push하고 원격 CI 결과를 확인한다.
9. staging 배포와 smoke test를 통과한다.
10. 별도 승인 후 production에 배포하고 health check를 확인한다.
11. 어느 단계에서 실패하더라도 상태, 로그, 입력과 변경 결과를 잃지 않고 재개하거나 복구할 수 있다.

## 결론

현재 문서상 아키텍처와 실행 기반은 최종 형태로 가기에 적절하다. 구조를 다시
처음부터 설계할 필요는 없다. 다만 앞으로의 중심은 Git 명령 자동화가 아니라
Task Graph, 실행 복구, 독립 Reviewer, Commit Queue와 문서 기반 계획 자동화여야 한다.

현재 구현과 문서의 기준선 검증, 1단계 실행 안정성, 2단계 Task Graph 계약과 사람의
계획 검토·편집·확정 지점은 완료했다. 관련 문서 문맥 수집, 실제 변경 범위 강제,
경로 충돌 예측과 실행 순서 검증, 실행 결과·통합 검증 시도 기록, Commit Queue의
의존성·위험도 순서와 실패 귀속 근거도 추가했다. 다음에는 문서 증분 수집과 배포
오케스트레이션을 순서대로 추가한다. 이 순서를 유지하면 현재 기반을 버리지 않고
최종 목표로 점진적으로 발전시킬 수 있다.

# 기획 준비·기능 계획·Task 변경 흐름: 73~82단계

**상태: 73~82단계 완료. 이번 10단계 묶음의 구현·국소 확인·기록을 종료했다.**

## 목표와 승인 범위

사용자의 다음 10단계 진행 요청에 따라 73~82단계를 수행한다. 앞선 1~72단계 완료 기록과
기존 미커밋 변경을 보존한다. 시작 Pipeline은 7,766줄이며 아래 세 흐름을 분리한 뒤 종료한다.

## 책임과 영향 범위

- 기획 준비 모듈은 명시적인 설정 값과 정규화/가용성·준비 확인/색인 조회 callback으로 입력과
  원문/색인·초기 RunState를 준비한다. 예약 ID의 존재 검사와 실제 Git 조회, maturity/스타일 검사,
  초기 정책 저장·PLANNING 시작과 최종 REVIEWED 전이는 Pipeline에 남긴다. snapshot은 원래 위치와
  호출 순서로 기록하며 저장 형식·파일명은 바꾸지 않는다.
- 기능 계획 모듈은 검증된 bootstrap/기술 결정의 일치·요청 문맥과 모델 결과를 검증/조합한다.
  SDK 대화 수명, 실제 계획 생성, 시도/실패 기록과 최종 Run 단계 전이는 Pipeline이 소유한다.
- Task 적용 모듈은 기존 병합 규칙을 재사용해 변경 전 snapshot·기획 입력·결과/실패 기록을 다룬다.
  기존 run/기획 잠금, 실행 준비/Git와 최종 단계 결정은 Pipeline에 남긴다. 전체 Pipeline/Store/Config를
  전달하지 않으며 실제 파일/상태 쓰기는 제공된 경로나 좁은 기록 API로 한정한다.
- `pipeline.py`, 명시적인 `planning` 하위 모듈과 필요한 기존 순수 API/아키텍처·관련 테스트만 다룬다.
  공개/기존 private signature·예외/문구·저장/CLI/RPC/MCP 계약과 실패를 드러내는 방식은 유지한다.

## 검증

이동 전 snapshot과 AST로 본문·callback·기록/오류 순서를 대조한다. 수정 파일의 `py_compile`과
전역 참조·줄 길이/공백·diff를 확인하고, 기존 기획 준비/색인·기능 계획·동일 그룹 적용 테스트 중
변경 경계만 선택한다. 새 경계가 기존 사례로 관찰되면 테스트를 추가하지 않는다.
통과한 검사는 후속 변경의 영향을 받지 않는 한 반복하지 않는다.

전체 테스트/renderer·빌드/패키징·실제 AI/계정/도구/화면·다른 저장소/Rust/공개 checkout과
commit/push/deploy는 이번 작업에 포함하지 않는다.

## 진행과 결과

### 73~75단계: 최초 기획 준비

- `PlanningPreparation`과 초기 검증 설정/준비 결과 DTO에 입력 정규화·provider 준비 확인·문서/색인·
  초기 상태 구성을 묶었다. 원문/색인 snapshot 기록도 별도 함수로 옮겼다. 예약 ID 검증과 실제 Git
  확인은 Pipeline에 유지했고, maturity/스타일·초기 정책과 최종 전이는 원래 위치/순서다.
- `pytest -q tests/test_pipeline.py tests/test_effort_planning_binding.py`에서 기획 준비 후 저장,
  문서 없는 지시, 준비된 색인 재사용, 초기 정책 선저장, docs-only와 모호한 프로젝트 의도 관련
  `-k` 선택을 실행해 `6 passed`(4.21초)였다. 테스트/기대값은 추가하거나 변경하지 않았다.

### 76~78단계: 검증한 기본 구조의 기능 계획

- `FeaturePlanningBaseline`과 세 함수로 기본 구조/기술 결정의 일치·요청 문맥·계획 결과 검증과
  root Task의 기본 구조 의존성 부여를 옮겼다. SDK 세션 종료·실제 기획·시도 횟수·성공/실패 저장과
  VERIFIED/PLANNED 전이는 Pipeline에 남겼다. 모델이 bootstrap을 재생성하는 경우의 거부도 같다.
- `pytest -q tests/test_pipeline.py -k 'verified_bootstrap_generates_feature_plan or
  feature_plan_failure_preserves_verified_bootstrap'`를 실행해 `2 passed`(0.87초)였다. 완료 Task와
  기술 결정·검증 근거 및 재시도 상태를 기존 사례로 확인했다.

### 79~81단계: 같은 그룹의 Task 변경 입력과 기록

- `TaskChangeSnapshot`과 `PendingTaskChanges`로 변경 전 근거/요청 snapshot·요청 선택/claim·
  계획 생성과 기존 병합 규칙·성공/실패 receipt를 나눴다. Pipeline은 잠금 아래 실제 Task 준비와
  계획 산출물 쓰기·단계 결정·실패 시 Task/단계/요청 복원을 원래 순서로 수행한다.
- `pytest -q tests/test_pipeline.py`에서 완료/실패 실행 근거 보존·잘못된 계획의 복원·완료 그룹의
  새 작업·실행 중 변경 대기·실패 receipt·대화 snapshot 대기의 기존 `-k` 선택 6개를 확인했다
  (`6 passed`, 10.42초). 준비 대상 교집합과 오류/저장 순서도 AST로 대조했다.

### 82단계: 묶음 종료

- 이동 전 snapshot과 AST로 입력/문서/색인/기본 상태·기능 계획의 세 규칙·Task 변경의 snapshot/
  claim/병합/receipt 본문과 Root의 최종 단계/실행 준비/실패 복원을 대조했다. 새 내부 Git 조회 helper는
  기존 두 Git 호출만 수행한다. 기존 모든 Pipeline 서명과 범위 밖 메서드 416개가 그대로다.
- 수정 Python 4개 파일의 `py_compile`·전역 참조·변경 줄 길이/공백·diff를 확인했다. 공개 Pipeline
  112개·Store 91개·응용 API 121개 서명, 모델 80개와 오류/모델/기획 import·RPC 122개 경로를 확인했다.
  142개 코어 모듈의 import 선언에 순환/기능 모듈 역참조가 없고 신규 모듈은 전체 소유 객체를 받지 않는다.
  별도 프로세스에서 planning 기본 import가 SDK/Git/runtime을 로드하지 않는 것과 새 모듈 import도 확인했다.
- 관련 검사 합계는 14개다. 통과한 동작 검사는 반복하지 않았으며 새 테스트는 없다. 아키텍처에 신규
  준비/기능 계획/Task 적용 책임과 의존 방향을 반영했다.
- Pipeline은 7,766줄에서 7,559줄로 207줄 줄었다. 대상 함수는 각각 170→71줄, 124→72줄,
  105→47줄이다. 신규 준비/기능/적용 모듈은 각각 219/85/140줄이다. 전체 리팩터링의 완료를 뜻하지 않는다.
- 기존 미커밋 변경을 보존했다. 전체 테스트/renderer·빌드/패키징·실제 AI/계정/도구/화면·다른 저장소/
  Rust/공개 checkout·commit/push/deploy는 이번 범위에 필요하지 않아 수행하지 않았다. 추가 단계는 시작하지 않았다.

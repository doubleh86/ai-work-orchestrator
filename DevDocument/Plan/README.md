# 개발 계획 문서 규칙

계획 기록의 깊이는 변경 영향에 맞춘다. 아래 기준에 해당하면 구현 전에 이 폴더에
계획을 작성하거나 같은 목표의 기존 계획을 갱신한다. 계획 작성 자체는 승인 요청이 아니다.

## 별도 계획이 필요한 작업

- 여러 모듈에 걸친 기능·구조 변경 또는 의존 방향 변경
- 공개 CLI·RPC·설정 계약, 저장 형식, 상태 전이의 의미 변경
- Git 작업, 사용자 파일의 생성·이동·삭제, 외부 실행 등 부작용 범위나 승인 경계의 변경
- 영향 범위나 구현 선택의 불확실성이 커서 결정·진행 기록이 필요한 작업
- 사용자가 계획 문서를 요청한 작업

위 조건에 해당하지 않는 작은 버그 수정, 국소 리팩터링, UI 문구·배치,
동작을 바꾸지 않는 문서 수정은 별도 계획서 없이 진행한다. 이때도 목표·범위·검증 방법을
간단히 정리하고 완료 보고에 결과를 남긴다. 작은 수정이라는 이유로 계약·부작용 변경을
계획 대상에서 제외하지 않는다. 테스트용 임시 파일 생성은 그 자체로 계획서 작성 사유가 아니다.

## 공개 설계 문서

현재 구조와 계약은 `Docs/Architecture.md`, 사용자 흐름은 `README.md`를 따른다.
개인 프로젝트 기록과 비공개 기획 자료는 공개 저장소에 포함하지 않는다.

## 파일명

```text
yyyy-MM-dd-feature-name.md
```

## 문서 형식

목표, 범위와 영향 파일, 검증 방법, 진행·결과를 남긴다. 아래는 권장 형식이며 관련 항목을
합쳐도 된다. 참고 설계·미결정 사항·상태 전이·부작용·복구 방법은 해당하는 경우에만 추가한다.

```markdown
# 작업명

## 목표

## 범위와 영향 파일

## 검증 방법

## 진행과 결과
```

## 작성 기준

- 모듈 추가나 의존 방향 변경은 `Docs/Architecture.md`와 일치하는지 기록한다.
- 목표·계약·부작용·영향 범위가 실질적으로 바뀌면 해당 구현 전에 계획을 갱신한다.
  파일 목록이나 세부 구현 선택의 변화는 진행 기록에 반영하며 매번 작업을 멈추지 않는다.
- 완료 후 실제로 실행한 명령과 검증하지 못한 항목을 기록한다.
- 계획에 외부 실행이나 Git 부작용 변경이 포함되면 대상, 데이터 영향, 승인 지점과 복구 방법을 기록한다.
  이미 정해진 절차의 승인된 실행만으로 별도 구현 계획을 만들지는 않는다.

# 개발 계획 문서 규칙

계획 기록의 깊이는 변경 영향에 맞춘다. 아래 기준에 해당하면 구현 전에 이 폴더에
계획을 작성하거나 같은 목표의 기존 계획을 갱신한다. 계획 작성 자체는 승인 요청이 아니다.

## 별도 계획이 필요한 작업

- 여러 모듈에 걸친 기능·구조 변경 또는 의존 방향 변경
- 공개 CLI·RPC·설정 계약, 저장 형식, 상태 전이의 의미 변경
- Git 작업, 사용자 파일의 생성·이동·삭제, 외부 실행 등 부작용 범위나 승인 경계의 변경
- 영향 범위나 구현 선택의 불확실성이 커서 결정·진행 기록이 필요한 작업
- 사용자가 계획 문서를 요청한 작업

위 조건에 해당하지 않는 작은 버그 수정, 국소 리팩터링, UI 문구·배치,
동작을 바꾸지 않는 문서 수정은 별도 계획서 없이 진행한다. 이때도 목표·범위·검증 방법을
간단히 정리하고 완료 보고에 결과를 남긴다. 작은 수정이라는 이유로 계약·부작용 변경을
계획 대상에서 제외하지 않는다. 테스트용 임시 파일 생성은 그 자체로 계획서 작성 사유가 아니다.

## 공개 설계 문서

현재 구조와 계약은 `Docs/Architecture.md`, 사용자 흐름은 `README.md`를 따른다.
개인 프로젝트 기록과 비공개 기획 자료는 공개 저장소에 포함하지 않는다.

## 단계별 진행과 구조 변경

- 여러 단계의 계획은 현재 구현할 목표·영향 영역·공개 계약/저장 형식 변경 유무·검증과
  남은 단계를 구분한다. 계획 전체나 설계 질문의 답변을 모든 단계의 실행 승인으로 확대하지 않는다.
- 목표 전체의 구현 요청이나 여러 단계 승인이 있으면 그 완결에 필요한 단계를 진행한다.
  계획을 여러 단계로 나눴다는 이유만으로 중간 재승인을 묻지 않는다.
- `다음 작업`·`계속 진행`은 별도 지정이나 앞선 여러 단계 승인이 없으면 다음 한 단계를 뜻한다.
  승인 범위가 끝나면 결과와 남은 범위를 보고한다.
- 현재 단계에 필요하지 않은 후속 API·설정·worker·빈 패키지를 미리 만들지 않는다.
  한 단계는 검토 가능한 완결 단위로 잡고, 깨진 호출부·저장 호환을 알고도 남기는 식으로 나누지 않는다.
- 기존 구조로 충족할 수 있는지 먼저 확인한다. 핵심 모델·소유권·프로세스 경계가 달라지거나
  호환 부담이 커서 재작성·엔진 교체가 필요해지면 대안·데이터 호환·마이그레이션 영향을 기록한다.
  새로 필요한 사용자 결정만 확인하고, 승인된 구조와 영향 범위가 같다면 계속 진행한다.
- 구현 방법이나 예상 파일만 달라지고 목표·영향 영역·공개 계약이 같으면 필요한 기록을
  갱신하고 진행한다. 실질적인 기능·계약·데이터 처리·승인 범위 확장은 구현 전에 계획에 반영한다.

## 계획 문서의 수명

- `Plan/`에는 진행 중이거나 후속 구현·결정이 남은 계획을 둔다.
- 구현과 요청 범위의 검증이 끝나고 후속 구현·결정이 없는 문서는 `Completed/`로 분류할 수 있다.
  별도 실계정·제품 화면·배포 확인이 남으면 미수행 범위를 명시하고 해당 확인 완료로 표현하지 않는다.
- 폐기된 초안·대체된 이전 기준은 `Archive/`로 구분한다. 완료 기록과 폐기 기록을 섞지 않는다.
- 문서 이동은 해당 작업 범위에서만 하며 현재 링크·참조를 함께 맞춘다. 이 규칙을 이유로
  다른 작업의 계획을 일괄 이동하거나 과거 검증을 반복하지 않는다.

## 파일명

```text
yyyy-MM-dd-feature-name.md
```

## 문서 형식

목표, 범위와 영향 파일, 검증 방법, 진행·결과를 남긴다. 아래는 권장 형식이며 관련 항목을
합쳐도 된다. 참고 설계·미결정 사항·상태 전이·부작용·복구 방법은 해당하는 경우에만 추가한다.

```markdown
# 작업명

## 목표

## 범위와 영향 파일

## 검증 방법

## 진행과 결과
```

## 작성 기준

- 모듈 추가나 의존 방향 변경은 `Docs/Architecture.md`와 일치하는지 기록한다.
- 목표·계약·부작용·영향 범위가 실질적으로 바뀌면 해당 구현 전에 계획을 갱신한다.
  파일 목록이나 세부 구현 선택의 변화는 진행 기록에 반영하며 매번 작업을 멈추지 않는다.
- 완료 후 실제로 실행한 명령과 검증하지 못한 항목을 기록한다.
- 검증 방법은 [현재 검증 기준](../../Docs/Testing.md)에 맞춰 필요한 정적 검사와 관련 테스트만 적는다.
  전체 테스트·빌드를 기본 목록으로 나열하지 않으며, 필요하면 확대 이유를 적는다.
  과거 계획의 전체 검사·완료 기록은 후속 수정에서 같은 검사를 반복할 근거가 아니다.
- 계획에 외부 실행이나 Git 부작용 변경이 포함되면 대상, 데이터 영향, 승인 지점과 복구 방법을 기록한다.
  이미 정해진 절차의 승인된 실행만으로 별도 구현 계획을 만들지는 않는다.
